# 鉴权链路从0到1（大白话+图表版）

> 配套阅读：[`鉴权权限矩阵.md`](./鉴权权限矩阵.md)、[`API-接口索引.md`](./API-接口索引.md)

## 1. 先说结论：项目里有 4 层门禁

如果你只记一句话：这个项目不是“登录一次就完事”，而是“分层鉴权”。

1. 平台登录鉴权（你是谁）  
2. 平台 RBAC 鉴权（你能做什么）  
3. 工具调用二次门禁（运行时还能不能调工具）  
4. 外部 Gateway API Key 鉴权（外部客户端接入）  

```mermaid
flowchart TD
    A[用户/外部客户端发请求] --> B{请求类型}
    B -->|平台后台请求| C[Sa-Token 登录态校验]
    C --> D[RBAC 注解判权]
    D --> E{是否涉及工具调用}
    E -->|否| F[执行业务]
    E -->|是| G[tool:invoke 二次门禁]
    G --> H{风险等级 HIGH?}
    H -->|否| I[执行工具并审计]
    H -->|是| J[创建/复用审批单]
    J --> K[PENDING_APPROVAL]
    K --> L[审批通过后续跑]
    B -->|外部 MCP Gateway 请求| M[API Key 校验]
    M --> N[过期/限流校验]
    N --> O[SSE 会话建立 + JSON-RPC 路由]
```

## 2. 平台登录链路（你是谁）

### 2.1 登录时序图

```mermaid
sequenceDiagram
    participant FE as 前端登录页
    participant AC as AuthController
    participant AAS as AuthAppServiceImpl
    participant ICS as SaTokenIdentityContextService
    participant DB as IdentityRepository/DB

    FE->>AC: POST /api/auth/login(username,password)
    AC->>AAS: verifyLogin()
    AAS->>DB: findByUsername + BCrypt 校验
    DB-->>AAS: 用户信息
    AAS-->>AC: 校验通过
    AC->>ICS: login(userId) -> StpUtil.login
    AC->>AAS: recordLoginSuccess(userId, ip)
    AC->>AAS: loadProfile(userId)
    AAS->>DB: 查询 roles + permissions
    DB-->>AAS: 画像数据
    AAS-->>AC: AuthProfile
    AC-->>FE: tokenName/tokenValue/tokenTimeout/profile
```

### 2.2 大白话解释

后端 `AuthController.login` 干 5 件事：

1. 校验参数  
2. 校验用户名密码和账号状态（`AuthAppServiceImpl.verifyLogin`）  
3. 建立 Sa-Token 登录态（`StpUtil.login`）  
4. 记录登录时间/IP  
5. 返回 token + 用户画像（角色/权限）  

关键代码：
- `ai-mcp-knowledge-trigger/.../AuthController.java`
- `ai-mcp-knowledge-application/.../AuthAppServiceImpl.java`
- `ai-mcp-knowledge-infrastructure/.../SaTokenIdentityContextService.java`

## 3. 前端如何接住登录态

```mermaid
flowchart LR
    A[登录成功响应] --> B[Pinia authStore.setLogin]
    B --> C[localStorage 存 token/profile]
    C --> D[axios 请求拦截器]
    D --> E[请求头写入 tokenName: tokenValue]
    E --> F[后端鉴权]
    F -->|401| G[清空本地登录态并跳登录页]
```

关键点：

1. 前端不是写死 `Authorization`，而是按后端返回的 `tokenName` 动态塞请求头。  
2. 响应拦截器拿到 401 会自动清理本地态并重定向登录页。  
3. 路由守卫 + 按钮权限只是“体验层”，真正安全边界在后端。

## 4. RBAC 权限链路（你能做什么）

### 4.1 判权数据流图

```mermaid
flowchart TD
    A["SaCheckPermission 注解（xxx）"] --> B["Sa-Token 发起权限查询"]
    B --> C["SaTokenPermissionProvider.getPermissionList"]
    C --> D["AuthAppService.queryPermissionCodes"]
    D --> E["IdentityRepository.findPermissionCodes"]
    E --> F[(sys_user_role)]
    F --> G[(sys_role_permission)]
    G --> H[(sys_permission)]

    J -->|是| K["放行"]

```

### 4.2 数据关系图（简化）

```mermaid
erDiagram

    SYS_ROLE ||--o{ SYS_USER_ROLE : assigned_to
```

### 4.3 一句话规则

超管（`is_super_admin=1`）直接拿全部启用权限。

## 5. 工具调用二次门禁（最容易漏）

为什么会出现“接口有权限，但工具调用还是被拦”？  
因为工具在运行时还有独立门禁，不只看 Controller 注解。

### 5.1 决策流程图

```mermaid
flowchart TD
    A["进入工具回调 call()"] --> B["解析 runId/operatorId"]
    B --> C{"bypass 开启?"}
    C -->|是| D["跳过 tool:invoke 校验"]
    C -->|否| E{"有 tool:invoke 权限?"}
    E -->|否| F["DENIED + 记审计 + 记计数"]
    E -->|是| G["进入风险审批判断"]
    D --> G
    G --> H{"riskLevel == HIGH?"}
    H -->|否| I["直接执行工具"]
    H -->|是| J{"已有 APPROVED?"}
    J -->|是| I
    J -->|否| K{"已有 PENDING?"}
    K -->|是| L["抛 ApprovalRequiredException"]
    K -->|否| M["创建审批单并抛异常"]
```

### 5.2 两个实现入口

1. `GatewayToolCallbackProvider`：HTTP Gateway 工具  
2. `DynamicMcpToolCallbackProvider`：动态 MCP 工具  

两者都会校验 `tool:invoke`，并写工具审计与调用计数。

## 6. 审批续跑链路（PENDING_APPROVAL 怎么恢复）

```mermaid
sequenceDiagram
    participant Run as Agent/Workflow Run
    participant TP as ToolCallbackProvider
    participant AR as approval_request
    participant AC as ApprovalController
    participant AAS as ApprovalAppServiceImpl

    Run->>TP: 调用高风险工具
    TP->>AR: 查询 APPROVED/PENDING
    alt 无审批可放行
        TP->>AR: 创建 PENDING 审批单
        TP-->>Run: 抛 ApprovalRequiredException
        Run-->>Run: 状态改为 PENDING_APPROVAL
    end

    AC->>AAS: /api/approvals/approve
    AAS->>AR: 标记 APPROVED
    AAS->>TP: 用快照参数执行已审批工具（bypass）
    AAS-->>Run: 继续执行并收敛为 SUCCESS/FAILED
```

大白话：

1. 运行中遇到高风险工具就先挂起。  
2. 人工审批通过后，系统拿审批快照继续跑，不需要用户重新触发整条链路。

## 7. 外部 MCP Gateway API Key 鉴权链路

### 7.1 建连 + 消息时序图

```mermaid
sequenceDiagram
    participant Client as 外部 MCP 客户端
    participant GC as McpGatewayController
    participant GS as GatewaySessionService
    participant DB as mcp_gateway/mcp_gateway_auth
    participant GM as GatewayMessageService

    Client->>GC: GET /api/gateway/{gatewayId}/mcp/sse + X-API-Key
    GC->>GS: establishSseConnection(gatewayId, apiKey)
    GS->>DB: 校验网关启用 + API Key 有效 + 未过期 + 限流
    DB-->>GS: 校验通过
    GS-->>Client: SSE endpoint(sessionId)

    Client->>GC: POST /mcp/message?sessionId=...
    GC->>GM: process(JSON-RPC)
    GM-->>GC: initialize/tools/list/tools/call 响应
    GC-->>Client: SSE message 回推
```

### 7.2 核心规则

1. `mcp_gateway_auth` 有启用记录时，API Key 必填。  
2. 支持 `expire_time` 过期控制。  
3. 限流按 `gatewayId + apiKey` 做分钟窗口计数。

## 10. 排障决策图（建议按图排）

```mermaid
flowchart TD
    A[请求失败/调用异常] --> B{HTTP 状态码}
    B -->|401| C[检查 token 是否存在、是否过期、请求头是否带 satoken]
    B -->|403| D[检查账号权限集合是否包含目标 permission]
    B -->|200 但工具返回 PERMISSION_DENIED| E[检查 tool:invoke 与二次门禁]
    B -->|PENDING_APPROVAL| F[去审批列表处理审批单]
    B -->|外部 Gateway 报错| G[检查 API Key/过期/限流/网关状态]
    D --> H[核对用户-角色-权限三张关系表]
    E --> I[看 ToolCallbackProvider 审计日志]
    F --> J[审批通过后确认 run 是否续跑]
    G --> K[核对 mcp_gateway_auth 与 sessionId 生命周期]
```

## 11. 当前实现注意点（读源码时必看）

1. 权限查询 SQL 主要依赖 `sys_permission.status=1`，排查角色禁用生效时要结合实际 SQL。  
2. 用户状态校验发生在登录时；已登录用户是否立即失效要结合 token 生命周期看。  
3. 外部 Gateway 的 API Key 当前是明文存储，生产环境建议加密/哈希治理。  
4. 工具审批是运行时门禁，不是接口注解的替代，而是补充。  

---

## 12. 一句话复盘

真正的完整链路是：

登录鉴权（身份） -> RBAC（接口权限） -> 工具二次门禁（运行时权限） -> 审批续跑（高风险治理） -> 外部 API Key 鉴权（网关接入）。

四层一起看，才是这个项目的完整安全闭环。
